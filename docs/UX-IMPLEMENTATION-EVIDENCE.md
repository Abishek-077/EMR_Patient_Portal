# UX Implementation Evidence

This document maps the implemented EMR Patient Portal behavior to ten UX laws and Nielsen’s ten Usability Heuristics. Evidence uses the deterministic local demo dataset and the real authenticated API workflows.

## Demo access and deterministic setup

- Run `npm run seed:demo` to reset the local development database to the documented demo state.
- Patient evidence account: `patient@example.test` / `Patient@Test1`.
- Run `npm run test:ux` to reset the data, start isolated API and Vite servers, run the serial evidence tests in Google Chrome, and recreate all PNGs.
- Playwright uses a 1440×1000 viewport, 100% browser zoom, `en-NP`, `Asia/Kathmandu`, and reduced-motion preference.
- The test-only network interception delays the appointment request solely while screenshots 10 and 11 are captured. A test-only HTTP 503 produces screenshot 19. Neither behavior exists in production code.
- The screenshots contain only fictional seed data and never expose the password, bearer token, or developer tooling.

## Attention-state resolution

The dashboard service computes attention items on every request:

- A queued or pending refill disappears when its request status becomes terminal.
- A pending referral disappears when its referral status becomes terminal.
- A pending appointment request disappears after approval/rejection/cancellation; appointments requiring action disappear after their status changes.
- The billing item recalculates after payment and disappears when the outstanding total is zero. T6 proves this against the real payment endpoint.

The client never hardcodes an unresolved task or optimistic resolution.

## Genuine limitations

- Screenshot automation uses the locally installed stable Google Chrome channel because the bundled Playwright Chromium download was unavailable in this environment.
- The automated evidence set captures the required desktop viewport. T8 additionally verifies operability and absence of page-level horizontal overflow at 1024×768 and 390×844, but no separate tablet/mobile evidence images were requested.
- Keyboard behavior, focus movement/restoration, semantic names, live regions, reduced motion, and responsive overflow are automated. A dedicated axe scan and instrumented contrast audit are not part of the repository, so WCAG 2.2 AA is supported by implementation and focused checks rather than claimed as a formal conformance certification.
- Payment methods and clinical records are fictional local seed data; no external payment processor or production EHR is contacted.
